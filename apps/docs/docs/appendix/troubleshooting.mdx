## Database Connection Pooling

Open Mercato relies on PostgreSQL connection pooling to avoid "too many clients" errors. Tune the pool via environment variables to match your deployment footprint.

### Pool Configuration

- `DB_POOL_MIN` — Minimum connections in the pool (default: `2`)
- `DB_POOL_MAX` — Maximum connections in the pool (default: `20`)
- `DB_POOL_IDLE_TIMEOUT` — Idle timeout in milliseconds before a connection is released (default: `30000`)
- `DB_POOL_ACQUIRE_TIMEOUT` — Acquire timeout in milliseconds when waiting for a connection (default: `60000`)

### Recommended Settings

Production baseline:

```bash
# Adjust according to PostgreSQL max_connections
DB_POOL_MAX=20
DB_POOL_MIN=5
DB_POOL_IDLE_TIMEOUT=30000
DB_POOL_ACQUIRE_TIMEOUT=60000
```

Local development:

```bash
# Smaller pool for local workflows
DB_POOL_MAX=5
DB_POOL_MIN=1
DB_POOL_IDLE_TIMEOUT=10000
DB_POOL_ACQUIRE_TIMEOUT=30000
```

If you continue to hit connection limits, verify that background workers and migrations use the same pool settings, and confirm that your database `max_connections` value comfortably exceeds the aggregate pool size across all applications connecting to it.

## PostgreSQL auth errors on local setup

If local commands such as `yarn generate`, `yarn db:generate`, or app startup fail with errors like:

- `password authentication failed for user "postgres"`
- `role "postgres" does not exist`
- `could not connect to server`

you may be connecting to a different PostgreSQL instance already bound to `localhost:5432` (for example, a host-installed Postgres), not the Docker one started for Open Mercato.

### Fix

Start Docker PostgreSQL on a different host port and use the same port in `DATABASE_URL`:

```bash
POSTGRES_PORT=55432 docker compose up -d postgres
```

```env
DATABASE_URL=postgresql://postgres:postgres@localhost:55432/open-mercato
```

### Verify

```bash
psql "postgresql://postgres:postgres@localhost:55432/open-mercato" -c "select 1;"
```

If this succeeds but `:5432` still fails, keep using the alternate port (or stop the other local PostgreSQL service that occupies `5432`).

## Landing-page images after upgrading from legacy uploads

Landing-page images use the attachment partition root named `landingPageImages`. The production image and Compose service pin `ATTACHMENTS_PARTITION_LANDING_PAGE_IMAGES_ROOT` to `/app/apps/mercato/storage/attachments/landingPageImages`, outside Next.js's standalone working directory and inside the persisted `/app/apps/mercato/storage` mount. For more than one application replica, replace that path with a durable shared filesystem mounted at the same location in every replica; do not scale the filesystem-backed route across replicas with independent disks.

Before the first release containing this change:

1. Build the new `app` image without replacing the running container.
2. Enter a maintenance window and stop the old `app` container. Do not permit another landing-page image upload until the new image is running. A copy made while the old writer is live is not a release gate.
3. With both named volumes attached, create both absolute roots (even when the legacy inventory is empty), then make a final no-symlink copy from `/app/apps/mercato/uploads/page-images` to `/app/apps/mercato/storage/attachments/landingPageImages`. Preserve the exact organization/page/file hierarchy, then set directories to owner `1001:1001` mode `0750` and files to owner `1001:1001` mode `0640`.
4. Run the bundled checker from the new image while the writer remains stopped:

```bash
docker compose -f docker-compose.prod.yml run --rm --no-deps app \
  node /app/scripts/check-landing-page-image-assets.cjs \
  --root=/app/apps/mercato/storage/attachments/landingPageImages \
  --legacy-root=/app/apps/mercato/uploads/page-images \
  --require-legacy-parity
```

The two absolute roots are required; invoking the source-tree command without them fails rather than inspecting a checkout-relative empty directory. The checker reads image bytes only to validate runtime eligibility and calculate digests. It emits no path, tenant identifier, filename, or image content—only counts and aggregate SHA-256 values. Deployment remains blocked unless `ready` is `true`, `migrationRequired` is `false`, both roots are present, both trees have zero unsafe/unsupported/runtime-rejected entries, and their supported counts and digests match after the writer was stopped.

Start the new `app` only after this final parity gate succeeds. Keep the legacy volume unchanged for rollback. After the new version has served the copied assets successfully and the rollback window has closed, retire the legacy tree in a separate maintenance step. For later steady-state checks, omit `--require-legacy-parity`; the current root must still exist and pass every runtime-safety check.
